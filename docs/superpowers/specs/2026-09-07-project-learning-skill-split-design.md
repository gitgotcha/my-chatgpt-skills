# 项目深度学习与开发方案学习 Skill 拆分设计

## 目标

将当前 PR #15 中混合在 `backend-project-learning` 内的两种教学模式拆开。两者都能学习真实项目、源码和开发方案，唯一的产品差异是是否服务于专业面试：

1. 保留 `backend-project-learning`，用于明确面向专业面试的项目学习、面试问答与 STAR 训练。
2. 新建 `development-plan-learning`，用于不包含面试训练的项目、源码和开发方案学习。

两个 Skill 都采用循序渐进的对话节奏，但学习目标与完成标准不同。

## Skill 边界

| Skill | 主要输入 | 默认目标 | 默认输出 | 不负责 |
|---|---|---|---|---|
| `backend-project-learning` | 后端仓库、真实源码、需求、架构规格和实施计划 | 深入理解项目，并为专业面试形成可追问、可表达的项目能力 | Mermaid、源码索引、分层讲解、成功与失败案例、面试问答、STAR | 非面试模式下的普通项目学习 |
| `development-plan-learning` | 后端仓库、真实源码、需求、架构规格和实施计划 | 解释清楚用户的问题，通过核心理解题循序推进 | Mermaid 或关系表、问题解释、贯穿案例、1—3 个核心理解题 | 面试训练、STAR、自动修改方案或源码 |

## 路由规则

- 在选择 Skill 前，先确认用户本次学习是否面向专业面试和面试训练。上下文已经明确时不得重复询问；无法确认时只问一个简短问题。
- 用户需要专业面试学习、模拟追问、标准答案、项目表达或 STAR 训练时，使用 `backend-project-learning`。
- 用户不需要面试训练，只希望理解项目、源码、现有实现、优化方案、需求、架构规格或实施计划时，使用 `development-plan-learning`。
- 用户显式要求“进入面试场景”“按面试训练”时，立即切换到 `backend-project-learning`。
- 用户显式要求“剔除面试场景”“不要面试或 STAR”“只解释项目问题”时，立即切换到 `development-plan-learning`。
- 显式切换指令优先于此前会话模式；切换后保留已经建立的项目上下文和学习进度，不从头重复扫描或讲解。

## `backend-project-learning` 调整

以 `origin/main` 版本为能力基线，保留：

- 真实源码核验与准确文件行号；
- 完整业务闭环、成功与失败分支；
- 并发、一致性、事务、异步和性能深挖；
- 原理题、源码题、设计题和 STAR 训练；
- 用户明确授权后的源码学习注释。

教学节奏调整为分阶段推进：

1. 新模块先给小而闭合的 Mermaid 和学习索引。
2. 先讲业务职责与贯穿案例，确认用户能跟上。
3. 再进入关键源码、异常分支和专项机制。
4. 模块理解完成后进入面试题；用户作答后再给标准答案和追问。
5. STAR 放在模块末尾或用户要求时，不与首轮源码讲解同时倾倒。

用户追问局部问题时直接回答并返回主线；用户说停止时停止。保留深度内容，但分层揭示。

## `development-plan-learning` 设计

### 证据分层

每项结论标明来源：

- **现状事实**：由现有源码、配置、测试或部署证据验证；
- **方案要求**：规格或计划明确要求，但未必实现；
- **教学假设**：仅用于演示数据变化；
- **优化建议**：对方案的补充或替代，不能冒充已批准设计。

### 每个模块的教学闭环

1. 先用 Mermaid 或关系表建立当前模块的角色与边界。
2. 直接回答用户当前问题，解释输入、输出、状态和依赖。
3. 使用一个贯穿案例展示“之前—执行—之后”。
4. 涉及可靠性时增加一个最相关的失败、重试或并发分支。
5. 提出 1—3 个核心理解题，让用户用自己的话回答；先等待回答，不同时泄露答案。
6. 根据回答纠正具体误区，再进入下一模块。

同一模块的简短追问不重画全系统；关系变化时补局部图。图表、案例和正文各自承担不同信息，避免重复。

### 方案审阅边界

- 不能仅凭规格声称代码已实现或测试已通过。
- 当方案与源码冲突时指出差异，不擅自决定以哪一方为准。
- 解释锁、幂等、事务、队列或重试时说明成立条件，并用满足前提的例子说明。
- 默认只读；学习请求不授权修改方案、源码、部署或云端数据。
- 用户明确要求评审时可以列出缺口、风险和取舍；用户明确要求实施时转入相应开发工作流，不继续以教学模式代替实施计划。

## 行为测试

修改 Skill 前先运行对照样本，保存实际失败：

1. 深度项目学习场景：验证旧版本会不会一次倾倒所有层级；优化后应保留面试与 STAR，但循序推进。
2. 开发方案学习场景：在没有新 Skill 时，验证代理是否错误进入面试训练、把计划当实现或不给核心理解题。
3. 边界场景：规格与源码冲突、重复 Queue 通知、过期租约、用户停止、用户要求评审或实施。
4. 路由场景：同一个项目问题分别声明“用于专业面试训练”和“剔除面试，只理解问题”，应进入不同 Skill。
5. 显式切换场景：已在普通学习模式的用户要求进入实际面试时切到 `backend-project-learning`；已在面试模式的用户要求移除面试内容时切到 `development-plan-learning`，并保持当前学习进度。

每个主要输出形状用多个新上下文样本人工审阅；自动测试只验证包装、编码、链接和仓库契约，不能替代行为测试。

## 验收标准

- `backend-project-learning` 仍具有原版本的深度源码、面试和 STAR 能力，但首轮不会一次倾倒全部环节。
- `development-plan-learning` 能围绕项目、源码或开发方案逐步解释问题，每个模块先有图表，并留下 1—3 个核心问题；不生成面试题或 STAR。
- 两个 Skill 仅以是否需要专业面试学习与训练作为产品边界；路由前确认该需求，并服从用户显式切换指令。
- 两个 Skill 都保持规格与真实实现分离。
- 所有新增与修改资源为 UTF-8，相对链接有效，技能格式校验和仓库兼容性测试通过。
- 当前 PR #15 更新为上述拆分结果，不合并、不安装，等待用户审阅。
