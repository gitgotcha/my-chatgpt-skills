# 简历证据策略

本文件定义简历声明如何转化为可出题的知识点。所有判定都在提交 `submit_event` 之前完成，Worker 不负责推断证据。

## 三级证据

| 证据级别 | 判定 | 允许行为 |
| --- | --- | --- |
| 简历明示 | 简历中明确列出该技术、职责或成果 | 直接建立知识点并出题 |
| 项目强推断 | 由明确的项目类型、规模或职责可合理推出 | 只能条件式提问，或先请用户确认 |
| 无依据 | 简历没有对应线索 | 禁止进入题库 |

## 简历明示

简历明确列出某技术时，可以考察该技术的常见核心八股，不限于简历原句。例如简历写了 Redis，可以直接询问缓存穿透、击穿、雪崩、持久化与分布式锁。

可以考察“该技术的常见考点”，也可以考察“这个项目场景下你会如何用它”，但两者都不能被说成用户已经做过的事。

## 项目强推断

推断必须能追溯到简历已写明的项目事实。提问时使用条件式措辞，例如“如果项目需要防止重复执行，你会如何利用 Redis”。

用户确认后追加 `claim-confirmed`；用户否认后追加 `claim-rejected`。被否认的声明不再作为项目事实出题，后续题库版本必须排除它。

**不得把常见方案断言为用户在项目中实际使用过的方案。** 例如简历写了 Redis，可以问分布式锁的实现方式，但不得声称用户在项目里用了 Redisson 看门狗；不得把推测写成真实经历。

## 无依据

无依据的技术点不建立知识点、不生成题目。证据不足时减少题目数量并说明原因，禁止使用无依据的通用 Java 八股补齐题单。

## 无简历时停止

没有有效简历快照时，本技能必须停止出题并提示用户先上传简历。不得退化为通用 Java 八股，也不得用上一轮会话记忆冒充简历。

## 声明记录

每次处理简历生成新的 `resumeVersion`，保存结构化声明、声明之间的项目归属关系、技术标签、原文证据位置与文件指纹。历史题目、题单和评分继续绑定当时的 `resumeVersion`；新简历不覆盖旧版本。

简历原文件不入库，只保存结构化声明、证据位置、版本号和文件指纹。
