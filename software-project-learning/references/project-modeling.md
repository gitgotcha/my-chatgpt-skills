# 项目建模与学习路线

在首次接手项目、用户提出宽泛学习请求，或当前问题涉及多张表/多个组件时读取。目标是先建立最小但完整的业务模型，而不是生成目录清单。

## 证据分级

| 等级 | 可支持的结论 |
|---|---|
| E1：源码、配置、测试或运行结果 | 当前实现如何工作；运行结果仅在实际执行后声明 |
| E2：需求、架构规格或实施计划 | 方案要求和设计意图，不能证明已实现 |
| E3：从命名或结构得到的推断 | 待验证假设，必须说明验证入口 |
| E4：教学案例或模拟实现 | 仅用于理解，不属于项目事实 |

同一结论有多个来源时优先使用高等级证据；文档与源码冲突时并列展示，不静默替用户裁决。

## 建模顺序

1. **业务目标**：谁发起、想完成什么、最终可观察结果是什么。
2. **系统边界**：哪些组件在当前项目内，哪些是数据库、队列或第三方系统。
3. **责任模型**：区分业务事实、命令/任务、派生结果、通知和副本。
4. **状态模型**：列出关键状态、允许的迁移、触发者和失败后的停留点。
5. **关联模型**：解释业务主键、请求标识、事件标识、任务标识和游标各自解决的问题。
6. **关键不变量**：用一句可验证的话描述始终必须成立的条件。

表或组件问题使用以下关系表，不需要展示无关字段：

| 角色 | 保存/处理什么 | 谁写 | 谁读 | 关联键 | 何时变化 | 权威性 |
|---|---|---|---|---|---|---|

“权威性”需区分事实来源与可重建的派生数据。例如 Queue 通知通常不是业务事实的权威来源，Projection 通常可由事件重建。

## 学习路线

首次只给 3—7 个业务模块，按依赖顺序排列：入口与身份 → 核心事实 → 异步/派生 → 查询与回执 → 故障恢复与运维。每个模块列出目标、主要证据和完成标志；不要把每个文件变成一个模块。

对话内进度仅记录为：未讲、已讲、用户回答体现部分理解、用户回答体现理解。它不是持久化画像，也不能由“已经展示过”推断为“已经掌握”。
