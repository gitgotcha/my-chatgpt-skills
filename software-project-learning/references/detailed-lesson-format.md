# 详细单元讲解格式

在用户要系统学习一个模块、要求“细讲”，或主链路涉及多个服务/线程/状态时使用。以用户认可的“单元二”体验为质量标准：细节讲透、源码方便核对、范围收得住、节奏由学习者决定。技术判断保持专业严谨；非技术过渡可轻松一些，玩笑不能替代机制说明。并非每个小追问都要重复整套格式。

## 完整单元的输出顺序

一个完整单元按以下顺序组织；可以分轮展开，但不要为了塞满模板而重复整套大图：

1. **具体场景**：谁在什么业务动作里遇到这个问题，本轮讲到哪、不讲哪。
2. **可见时序图**：优先使用可直接渲染的 Mermaid `sequenceDiagram`，标清参与者、消息、同步/异步边界与响应；不要只给裸代码块、静态图片路径或泛化流程图。宽链路可拆主路径、冷加载、并发反例三张。
3. **源码定位**：按执行顺序给出文件、方法、起始行与“本处证明什么”，行号必须核验。
4. **源码级讲解**：代码节选保留真实分支与关键变量名，逐行或按紧邻代码行分组解释输入、条件、状态变更、返回值及下一跳；复杂行旁给教学注释，注释与代码语义一一对应。省略处明确标注；教学注释放在语句之外。
5. **状态与反例**：哪些状态被谁写入，反例从哪个时刻开始分叉；静态推演不得写成实测。
6. **取舍与验证**：最小修复、替代方案与代价，以及能抓住缺陷的测试设计；没运行就写 `not_run`。
7. **可口述答案**：一段可以直接讲给面试官听的闭环答案，区分源码事实与推断。
8. **底部一道追问**：只问当前最关键的一题，等待回答；用户没回答时不伪造答案、不产生 session 或 review。

合成完整样例见[余票查询完整对话样例](examples/ticket-query-rds-complete-dialogue.md)；项目学习与正式面试的快照读写见[RDS-JBryon 项目快照契约](rds-jbryon-runtime.md)。

## 一次讲一个闭环

开始时说明模块职责、本轮范围和暂缓内容。一个单元可以跨多轮或多次学习；不要为了单次回答完整而把相邻系统一并塞入。按学习者当前熟悉度调整，重点讲通因果和执行顺序，不做术语清单。

新业务模块先给一张可见时序图；只有纯判断分支才用流程图。Mermaid 图应直接作为 Mermaid 围栏输出以便客户端渲染。后续追问复用原图，只补发生变化的局部。随后用一个具体、可代入的案例说明：

| 时点 | 说明 |
|---|---|
| 操作前 | 请求输入、已有库存/记录/状态与相关角色 |
| 执行中 | 按真实调用顺序说明谁调用谁、传入什么、返回什么，以及做了哪些检查或写入 |
| 操作后 | 数据/状态落在哪里、由谁负责、请求方拿到什么结果 |

## 源码与索引要成对出现

静态代码教学都应提供以下两种阅读入口：

1. 代码围栏中的最小真实源码片段，保留足够上下文识别类、方法和条件；注明文件及方法。若是摘录、节选或删略，明确标注。伪代码和模拟实现需单独标识，绝不冒充仓库源码。
2. 独立的源码索引表，使用本地核验过的可点击**绝对路径与起始行号**。本仓库文档里的目标写成可移植占位 `<project-root>/...`，例如 `OrderServiceImpl.java`（`<project-root>/services/order-service/src/main/java/OrderServiceImpl.java:127`）；真实回答时先核验当次工作树，再输出实际绝对路径与行号。索引按调用顺序排列，解释每处代码证明什么；不要让读者只凭代码块猜文件位置，也不要只给路径却没有可读源码。

| 顺序 | 文件/行号索引 | 方法或语句 | 输入/结果/状态 | 本处证明什么 |
|---:|---|---|---|---|

沿执行顺序讲片段：逐行解释关键参数、返回值、条件分支、数据写入和下一跳；每段结束点明“为什么这样做、做完状态如何变化”。适度用轻松类比或小幽默带入，但紧接着落回真实代码机制，避免逐字翻译语法。用户要求直接展示代码时，答案正文必须有代码块，不能只给链接。

讲完整主链路时，索引节点数按证明完整调用顺序所需，不受局部源码问答的五节点预算限制；若链路过长，就按业务阶段分多轮，每轮保留自己的代码与索引。

## 讲清边界但不扩成旁支大全

结合当前案例说明必要的数据归属、同步/异步时点、线程执行者、本地事务和远程服务边界。每个新单元优先深入一个最相关的失败/并发场景，并指出保障成立的条件及其不覆盖的内容。邻接主题先记作后续入口，等用户确认并选择继续后再展开。

把事实按证据来源区分：真实源码、配置或测试；文档方案；教学假设；模拟实现；尚未实施的建议；用户本人经历。行号、运行结果、线上效果、指标和个人贡献都必须有相应证据，不得用类名或注释代替验证。

## 确认、问题和停课

如果相关会话或项目记忆已记录“先确认当前讲解，再继续追问/推进”的偏好，把它当作长期有效的门槛，无需用户重复要求。讲解后只简短收束并等待确认；确认以前不附加理解题、面试题或下一模块。收到确认后再出一道最关键的问题并等待回答。用户回答题目不自动代表其已确认后续讲解。

如果用户没有设确认门槛，长单元讲完后最多提出一道当前层级的问题。用户主动指出理解偏差或追问时，先回答当下问题，不趁机扩成新模块。

用户说“今天到这里”“信息量够了”或类似表达时立即收束：简短写明已讲到哪里、尚待讲/核验什么、下次从哪里继续；不追加题目，不追求原定时长。进度分别标记为**已讲过、已确认讲解、能独立解释/通过验收**。

## 完整输入/输出范例

需要观察完整单元如何从起始请求走到澄清、局部追问、复述反馈和停课时，读取[单元二完整示范对话](examples/unit-2-complete-dialogue.md)。它保留了被用户认可的真实主讲答复和前后学习者输入，展示格式怎样贯穿多轮，而不只是单条回答的标题模板。

需要观察“场景 → 图 → 源码 → 注释节选 → 状态与反例 → 取舍与验证 → 口述答案 → 一道追问”的单轮完整输出时，读取[余票查询完整对话样例](examples/ticket-query-rds-complete-dialogue.md)。该样例是合成教学材料：三张图是合成教学图，源码事实来自静态核验，并发结论是可推导的教学反例，不是实测。

范例中的 12306 事实只作案例材料，不能作为别的项目的答案。跨项目迁移只复用教学结构、证据纪律和确认/节奏动作；目标项目的角色、API、状态、机制、源码片段、路径、行号和失败边界都要重新核验。维护范例时不得将其缩写成格式清单或用虚构对话替代真实输入/输出。

## 输出自查

- 是否先画清模块关系，再开始解释？
- 图片是否直接显示，而不是只给 Mermaid 源码或文件名？
- 案例是否贯穿操作前、真实代码动作和操作后？
- 有源码时，代码块和核验过的路径/行号索引是否同时存在且相互对应？省略处是否标注？
- 调用顺序、关键输入/返回、状态变化与至少一个反例是否清楚？
- 取舍与验证是否分开，未运行的验证是否写成 `not_run`？
- 口述答案是否区分源码事实与推断，并给出成立条件？
- 底部是否只有一道追问，且没有在用户回答前伪造答案或构造 session？
