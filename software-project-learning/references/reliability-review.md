# 可靠性、并发与优化审查

用户讨论事务、幂等、重试、Queue/Outbox、并发、缓存一致性、性能限制或已有实现优化时读取。两种学习模式都可使用。

## 审查范围

先回答用户点名的 1—3 个风险，不自动完成整套架构审计。局部问题默认使用一组不变量、一个必要的故障矩阵或并发时间线、一个贯穿案例和一个核心问题；其他风险只列为后续方向。用户明确要求全面评审时再覆盖所有维度。

## 先写不变量

先用可验证句子定义正确性，例如：“一个业务事实至多落一份，但同一任务允许被重复通知”“画像游标只能在前序事件均已纳入后推进”。没有不变量时，不能只凭流程顺畅判断方案正确。

## 故障矩阵

对跨边界流程只列当前问题最相关的失败点：

| 失败点 | 已持久化状态 | 权威记录 | 重试从哪里开始 | 幂等依据 | 对用户的真实回执 |
|---|---|---|---|---|---|

区分受理、处理完成和副本完成；`accepted`、入队成功或 HTTP 2xx 不能自动代表全部异步副作用已完成。

## 并发时间线

并发分析按 A/B 两个执行者列出：读取版本 → 本地计算 → 条件提交 → 影响行数/冲突 → 重读或放弃。只检查“新值更大”通常无法防止两个消费者基于同一旧版本覆盖；需要锁、版本号/CAS、单写者或等价提交保护，并说明锁粒度、租约失效和旧持有者继续执行的问题。

## 幂等与重试

分别解释：

- 请求标识：关联一次网络尝试及其重试回执；
- 事件标识或业务键：识别同一个业务事实；
- 任务标识：识别同一个派生工作；
- 消费去重或游标：避免重复副作用。

稳定标识只有与唯一约束、原子冲突处理或条件更新结合才构成保障。重试必须复用相同身份，不得用新 ID 把一次重试伪装成新业务。

## 优化评审

比较方案时至少覆盖：正确性、实现复杂度、恢复方式、并发行为、外部 I/O、可观测性、迁移/回滚成本。性能建议先给工作负载假设，再分析数据库往返、外部子请求、批大小、索引、热点、背压和最坏路径预算；没有测量不得承诺收益。

每项建议使用以下结论形状：

```text
当前证据 → 风险及触发条件 → 最小改进 → 替代方案与取舍 → 验证方式 → 未覆盖风险
```

用户要求实施时，学习阶段只先明确证据、范围和验收标准；实际修改进入相应开发流程，不以教学回答替代测试和发布验证。
